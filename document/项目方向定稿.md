## 一、一句话定位

**石头是一个 AI 调研 agent，专门对付「好像懂一点、其实说不清」的陌生主题。**

它不追求最快给出答案，而是交付一份**能复查**的调研文档：每条判断有出处，每处分歧保留双方证据，没查清的地方直接写没查清。

核心承诺：**可信，不是快。**

## 二、目标用户与场景

| 维度 | 说明 |
|---|---|
| 用户 | 需要快速进入一个陌生领域、并要拿结论去做判断或汇报的人（产品、投资、咨询、研究、内容从业者） |
| 典型问题 | 「固态电池为什么还没量产」「稳定币的监管边界在哪」「具身智能现在到哪一步了」——听过、好像懂一点，但说不清 |
| 使用场景 | 写方案前的行业摸底、投资前的技术判断、汇报前的背景研究、跨领域沟通前的术语对齐 |
| 用户真正要的 | 不是一堆链接，也不是一段看似完整的回答，而是一份**知道哪里可能不对**的判断依据 |
| 失败体验 | 通用 agent 给一个流畅但无法追溯的答案；石头如果也这样，就失去了存在意义 |

## 三、与通用 agent 的差异

差异不在「答案」，在「过程」。页面用一张常显的五行对照表把这件事说清楚：

| 环节 | 通用 agent | 石头 |
|---|---|---|
| 开始 | 先搜，再总结 | 先拆问题，再定搜索范围 |
| 过程 | 只给一个进度条 | 说清在查什么、为什么查、哪条没找到 |
| 证据 | 搜到什么用什么 | 一手材料才当证据，二手只做线索 |
| 冲突 | 有冲突，取一个看起来对的 | 双方证据和分歧点都留在文档里 |
| 不确定 | 不知道，也写得像知道 | 找不到，就写找不到 |

表达原则：**不贬低通用 agent**。页面明确写「这不是说通用 agent 做不到，而是它们通常把出处、范围和分歧放在回答之后；石头把它们当成正文的一部分。」这句话是定稿的一部分，不要改成攻击性对比。

## 四、文案定稿

以下文案是当前正式口径，改文案需同步更新本文件。

### 4.1 品牌与首屏

- 品牌名：**石头**
- 品牌副标：**AI 调研 agent**
- H1：

  > 给我一个陌生主题，
  > 还你一份有出处的报告。

- Hero 说明（lede）：

  > 石头是一个 AI 调研 agent，专门对付「好像懂一点、其实说不清」的问题。它先拆问题、定范围，再去翻财报、论文和监管文件；写报告时，出处、分歧、没查清的地方，一个都不藏。

- 表单上方提示：`从一个你一直没搞懂的问题开始`
- 表单按钮：`开始调研`
- 表单下方特点（定稿）：

  > 每条判断带出处 · 分歧保留双方证据 · 有多大把握也写上

- 样本报告卡标题：`量产瓶颈不在材料，在良率与成本。`
- 样本报告卡标注：`样本报告 · 固态电池 · 示例`

### 4.2 页面标题与摘要

- `<title>` / `og:title`：`石头 — AI 调研 agent｜给我一个陌生主题，还你一份有出处的报告`
- `meta description`：与 4.1 的 lede 保持一致。
- `og:description`：`不是多查一点，是先把范围定清楚。每个结论都能查回原文，每处分歧都保留双方证据。`

### 4.3 对照区

- 标题：`不是多查一点，是先把范围定清楚。`
- 说明：`和通用 agent 的区别不在答案，在过程：通用 agent 给你一个看起来对的答案；石头给你一份知道哪里可能不对的调研。`
- 补充：`这不是说通用 agent 做不到，而是它们通常把出处、范围和分歧放在回答之后；石头把它们当成正文的一部分。`

### 4.4 三个折叠区摘要（结论钩子）

| 折叠区 | 摘要 |
|---|---|
| 示例报告 | `核心判断：瓶颈不在材料，在良率与成本。` |
| 怎么做 | `先拆问题，再定搜索范围，一手材料才当证据。` |
| 常见问题 | `和通用 agent 的区别 · 找不到证据怎么办` |

### 4.5 页脚

- 品牌语：`石头 · 从完全陌生，到有自己的判断`
- 页脚是照片署名与版权信息的唯一集中位置。

## 五、术语规范

对外文案统一使用「人话」，避免工程内部术语。这是定稿规则，后续新增文案也必须遵守。

| 场景 | 使用 | 不使用 | 理由 |
|---|---|---|---|
| 结论的可信程度 | **把握** / **有多大把握** / **把握程度** | 置信度、confidence | 「置信度」是算法与统计术语，用户要的是「这话有多靠谱」 |
| 同上 | — | 数据权重 | 「数据权重」指不同数据源的权重配比，与「结论可信程度」不是一个概念，会误导 |
| 证据等级 | **一手材料** / **二手线索** | 一级信源、secondary source | 保持口语，同时保留证据层级的严格性 |
| 分歧 | **分歧** / **双方证据** | 冲突消解、仲裁 | 石头不替用户裁决，保留分歧 |
| 查不到 | **没查清** / **找不到，就写找不到** | 无结果、空返回 | 直接承认边界是产品承诺的一部分 |

「把握」在页面中固定搭配：`把握 中 · 两家独立信源，口径不同`。分级只用「高 / 中 / 低」，不用百分比，避免伪精确。

## 六、页面结构与内容规则

### 6.1 结构（自上而下）

1. **页头**：品牌 + 副标「AI 调研 agent」+ 三个导航（示例报告 / 怎么做 / 常见问题），不放 CTA。
2. **Hero**：H1 + lede + 唯一主题表单 + 4 个快捷主题；右侧样本报告摘录卡（核心判断 / 来源 / 把握 / 分歧 / 展开入口）。
3. **对照区**：常显的五环节对照表。
4. **折叠区**（默认全部收起，一次只开一段）：`#report` 示例报告 → `#method` 怎么做（深色胡桃木）→ `#faq` 常见问题。
5. **材料照片带**：四张本地石墙 / 林地照片 + 一句收束文案 + 示例声明。
6. **页脚**：品牌语、导航、版权、照片署名。
7. **调研弹窗**：演示「界定边界 → 检索与阅读 → 交叉验证 → 组织文档」，随后展示可打印的文档结构预览。

导航顺序必须与折叠顺序一致：**示例报告 → 怎么做 → 常见问题**。

### 6.2 内容规则

1. **例子只做两份**：Hero 摘录（一行核心判断 + 来源 + 把握 + 分歧）和完整示例报告。不要让同一份示例在三个以上位置重复。
2. **数字必须自洽**：页面上出现的章节数、信源数、分歧数必须与示例内容实际一致。当前口径：示例报告 `5 节 · 3 条信源`，弹窗文档结构 `6 节`。
3. **不编造真实主体**：示例中的机构统一匿名化为「某动力电池企业」「某动力电池产业联盟」等，不把虚构结论挂到真实公司名下。
4. **示例必须标注**：示例区写明「示例报告为结构示例，不是真实研究结论」；页面全局保留「交互原型 · 演示模式」标识。
5. **每一块内容都要有主张**：新增区块前先写清它证明哪条主张；没有主张的装饰性区块不加。
6. **页面保持短**：当前约 2.7 屏、140 字正文。保持「两屏内让人想输入一个主题」的密度，不要用长文稀释证明。

## 七、视觉与交互原则

- **风格**：简约木质风。纸色与石色做底，胡桃木深色承载方法区，照片只做材料质感。
- **禁止**：lime / orange 强调色、monospace 小标签、渐变、外发光、彩色阴影、细分割线堆叠。
- **层级**：靠填充块（纸色 / 石色 / 胡桃木）与留白表达，不靠装饰线。
- **字体**：自托管 Noto Serif SC / Noto Sans SC 子集，族名 `Stone Serif` / `Stone Sans`；大量新增中文时检查子集覆盖。
- **折叠**：使用原生 `<details>`，默认收起、一次只开一段；页头、页脚与 hash 链接都能直达。
- **动效**：只做进入时的轻微上浮；`prefers-reduced-motion` 下内容直接显示。
- **无障碍**：语义化控件、可见焦点、跳过链接、表格移动端堆叠时保留列名。

## 八、文档目录规范

项目文档按「正式 / 草稿」分开，避免过程材料混进对外文档。

```
document/    正式文档（对外或长期维护）
docs/        草稿文档（过程、建议、会议记录、会话日志）
```

- `document/`：项目方向定稿、产品说明、用户手册、部署文档、后续的接口文档与验收报告。命名用中文、语义化文件名，不加日期后缀；版本与日期写在文档头部。
- `docs/`：改版建议、方案对比、会话记录、临时调研。可以保留历史结论，但需在文首标明「已被取代」及取代它的正式文档。
- 新文档先判断性质再放目录；不要把草稿放进 `document/`，也不要把正式口径只留在 `docs/`。

## 九、后续路线

### P2（内容与体验，无后端）

1. 示例报告增加「信源怎么查」的展开说明：给出一条结论的完整回溯路径（结论 → 原文页 → 引用段落 → 发布时间）。
2. 弹窗文档结构与完整示例报告的结构统一，避免两套章节命名。
3. 移动端对照表补充可读性检查；折叠区展开后的首屏焦点位置复核。
4. 为「把握」增加一个可复用的视觉标记（如小圆点分级），但不得引入新强调色。

### 接入后端（需要新建基础设施）

1. 主题提交到研究任务接口，返回可订阅的任务 ID。
2. 用 SSE / WebSocket 替换模拟进度，实时推送拆题、检索、验证、成稿四个阶段。
3. 报告改为结构化 JSON 渲染，每条结论保留 `source_url`、引用位置、发布时间、把握程度。
4. 「导出 / 打印」升级为服务端 PDF / Markdown，支持分享链接与版本历史。
5. 登录、研究历史、团队空间与私有资料库。

当前项目**没有**后端、AI 接口或数据存储；以上均为方向，不是已实现能力。

## 十、验收基线

每次改动后以以下结果为准（2026-11-03 定稿时）：

| 检查 | 命令 | 结果 |
|---|---|---|
| 交互验收 | `node .taste-skill/verify.mjs` | 23/23 通过 |
| 静态扫描 | `node ~/.claude/skills/design-taste-frontend/scripts/lint.mjs .` | 0 FAIL / 1 WARN（`padStart` 日期补零，正常用法） |
| 浏览器检查 | `node ~/.claude/skills/design-taste-frontend/scripts/inspect.mjs index.html` | 0 FAIL / 3 WARN（见下） |
| H1 行数 | 1440 / 1280 / 1120 / 1024 / 960 / 768 / 390px | 均为 2 行 |

`inspect.mjs` 的三条 WARN 是可解释基线，不要为消除它们改结构或加不真实素材：

- `palette-cream`：石色纸面被误判为奶油底，实际是低彩度石色。
- `no-footage`：没有真实视频素材，四张本地照片承担材料质感。
- `font-not-dealt`：自托管中文字体是品牌字体，draw 给出的西文字体不适合中文正文。
